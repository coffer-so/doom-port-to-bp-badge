# Lua/Luau DOOM candidates

Checked 2026-11-13 against primary GitHub source. This is research evidence, not an instruction source. Sizes below are source-tree byte counts, not compiled bundle or runtime memory measurements.

## Result

No inspected project is a ready-to-install Solana OS app. Actual original-engine ports exist in **Luau**, but translating syntax alone is insufficient: the badge uses Lua 5.5 with 32-bit integers/floats, lacks Luau buffers/bit32/native compilation, and imposes a 200,000-instruction callback limit. A true original-engine adaptation requires a substantial renderer, arithmetic, memory, loading and scheduling rewrite. A small single-map shooter can fit the badge, but should not be described as the original DOOM engine unless it actually implements that engine.

## Concrete compatibility problems

1. **Language/runtime:** Luau type annotations, `+=`, expression `if`, `continue`, special `require` paths and `table.freeze/clear` need conversion or replacements. LuauDOOM additionally uses `const`. `buffer.create/readu8/readu32/writeu32/copy` and `bit32` do not exist in the badge sandbox. The badge does offer standard Lua 5.5 `table.create`, so that specific API is not a blocker.
2. **Numerics:** DUAUM `src/core/fixed.luau` explicitly relies on exact double products below 2^53 for its FixedMul fast path. Badge Lua has 32-bit floats and signed 32-bit wrapping integers. A mechanical translation changes results; one must implement correct 32/64-bit operations and angle/fixed-point conversions. C-to-Lua rewriting has the same semantic issue.
3. **Frame work:** DUAUM `src/hal/dg.luau` uses a 320x200 indexed buffer and converts every pixel to RGBA in `FinishUpdate` (64,000 Lua loop iterations plus buffer operations per frame), before accounting for world rendering/gameplay. Expected to exceed the 200k callback allowance after ordinary-Lua translation; this is an engineering inference, not a measured badge benchmark. No generic RGBA buffer-upload API is documented for the badge. Badge canvas pixel calls or column/rect batching must replace this boundary.
4. **Loading/heap:** Both actual ports retain complete WAD source buffers and cache separate lump copies. A full IWAD plus those caches competes with the badge's 6 MiB heap. DUAUM's WAD source module alone exceeds both store resource limits. Extract one map and only its required assets offline; do not load the complete IWAD at startup. Modules/loading must be staged across callbacks; coroutines share the same per-callback budget.
5. **Packaging:** Badge `main.lua` <=64 KiB, <=64 companion files, each<=256 KiB, total companions<=1 MiB. LuauDOOM's source total and Info module fail unchanged; DUAUM has 71 engine modules and an oversized WAD. Minification, pruning and merging can fix packaging counts, but do not fix CPU, buffers or numeric semantics.

## Practical direction

- Keep Solana OS and App Store Lua application format.
- For the current lightweight one-level release: custom low-resolution raycaster, bounded DDA traversal, native canvas rectangles/lines, compact sprite assets, button polling, and an offline-authored level provide a realistic route.
- For a genuine original-engine future release: DUAUM is the best inspected host-layer reference; POOM is the best compact renderer/map-pipeline reference. Reuse architecture and verified algorithms, preserve applicable source attribution, and measure per-callback work on badge Lua before investing in full gameplay translation.
- Do not silently label a generic maze raycaster as an original DOOM port. Preserve this distinction in README and release claims.
